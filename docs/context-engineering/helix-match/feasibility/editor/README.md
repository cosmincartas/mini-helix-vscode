# T1-C editor feasibility evidence (helix-match Task 1)

Experimental evidence only: no production behavior, keybinding, Helix logic or contract was changed. Missing evidence is marked pending.
Raw logs (large) live outside the repo: `/tmp/hm-t1c-logs/<version>/` (`run.log`, `trace.log`, `stdout.log`, `probe*.json`, `vscode-logs/`). Compact per-version results: `results-1.143.1.json`, `results-1.85.2.json` (generated by `summarize.js`).

## Host and method

- Host: Linux 7.2.5 (Fedora 44), display `:0` (no xvfb), x86_64, Node 26.8.2 (test runner) with the Node bundled in each VS Code. Another worker ran cargo concurrently, so timings are not clean.
- VS Code under test: **1.143.1** (current stable, textarea replaced by `native-edit-context`) and **1.85.2** (engines `^1.85.0` minimum; downloaded via `@vscode/test-electron` into `.vscode-test/vscode-linux-x64-1.85.2`).
- Each run: isolated profile, test-only user `keybindings.json` (768+ generated bindings carrying the logical character as args, gated on `miniHelixProbe.*` context keys), real renderer input over CDP (`Input.dispatchKeyEvent`, `Input.insertText`, `Input.imeSetComposition`). The existing extension stays active (NORMAL blockers etc.). Probe-owner commands and the temporary `type`/composition handlers are registered from the extension-test code. Settings added: autoClosingBrackets/Quotes/autoSurround `never`.
- Commands (from repo root):
  - `npm run compile`
  - `node out/test/feasibility/editor/runEditorProbes.js --version 1.143.1 --probes 1,2,3,4,5,8`
  - `node out/test/feasibility/editor/runEditorProbes.js --version 1.85.2 --probes 1,2,3,4,5,8 --startup-wait 0`
  - `node out/test/feasibility/editor/summarize.js /tmp/hm-t1c-logs/<v> <docs>/results-<v>.json`
  - Probe numbers: 1 Unicode, 2 modified routing (8 = fresh-host copy of its "outside session" part), 3 replay, 4 projection, 5 stale edit.
- Probe 4 was re-run alone after the final full run (adds sentinel selections, see its limits); its result file replaced the full-run copy.

## 1. Unicode input mechanism

Configs: A scoped bindings only; B `type` handler only while NORMAL bindings stay active; C `type` handler only with the extension's NORMAL contexts disabled (simulated with `setContext miniHelix.mode`); D bindings + `type` handler. Per-case pass = owner received exactly the expected scalar once and the document did not change. Counts are pass/total on 1.143.1 (1.85.2 equal except where noted).

| Group | A | B | C | D |
|---|---|---|---|---|
| printable ASCII incl. shifted punctuation (95) | 95 | 0 (NORMAL `a c d i u` run edit/insert commands; the rest are noop-blocked) | 95 | 95 |
| non-ASCII via key event with text (é ß ł « » 😀 𝒜 ñ Ж 日) | 0 (leaks into document, NORMAL does not block non-ASCII) | 10 (1.85.2: 8) | 10 (1.85.2: 8) | 10 (1.85.2: 8) |
| same via `Input.insertText` | 0 | 10 | 10 | 10 |
| layout simulation (physical code with non-US char) | 0 (binding fires for the US key: `2`, `-`) | 0 | 2/6 | 0 (binding wins) |
| combining mark | 0 | 1/2 | 1/2 | 1/2 |
| dead-key / IME composition (4 cases) | 1 | 3 | 4 | 3 |

- 1.85.2 differences: a CDP key event whose text is a non-BMP scalar (😀, 𝒜) reaches `type` as a garbled lone surrogate / empty string. `insertText` delivers them intact. Treated as a CDP-injection artifact for Chromium 114; not shown to occur with a real keyboard. The handler must validate "exactly one Unicode scalar" regardless (spec requires it).
- Mechanism facts (both versions): overriding `type`, `replacePreviousChar`, `compositionType`, `compositionStart`, `compositionEnd` works from an extension; delegating with `executeCommand('default:<name>', args)` is exact. Composition arrives as `compositionStart`, one `type` with the first composing text, then one or more `replacePreviousChar` (replaceCharCnt=1), then `compositionEnd`. The owner must keep only the final composing text and emit it at `compositionEnd`; intermediate payloads are not characters. With that rule the cases `´`->`é`, `に`->`日` and a cancelled (empty) composition produced exactly the expected scalar, no document leak and no duplicate (config C 4/4).
- A combined emission `e` + U+0301 through `insertText` arrives as one `type` with two scalars (must be rejected by "single scalar" validation); two key events arrive as two separate `type` calls.
- Outside a guarded session, with the handler registered, INSERT typing (`q`, `Q`, `é`, `😀`) and both compositions delegated and typed exactly once (events recorded, doc `qQé😀é日...`). After the handlers were disposed, INSERT typing (`q`, `é`, composition) typed exactly once; NORMAL `x` stayed blocked.
- Baseline finding (not caused by the probe): in NORMAL, with no session, non-ASCII text (`é`) is typed into the document. The existing blockers only cover ASCII keys.
- Layout/AltGr limits: CDP cannot reproduce OS layouts. With physical `code` Digit2/Minus the US-keymapped host resolves bindings to `2`/`-`, so a binding route delivers the wrong character; the `type` route delivers `é`/`ß` correctly (C). AltGr emulations (Ctrl+Alt flags with text, also separate `char` events) reach no `type` at all and hit `ctrl+alt+<key>` bindings in A/D. **Real non-US layouts and AltGr are PENDING** (needs an OS layout switch, intentionally not done on the user's display).
- Determination: scoped keybindings alone cannot deliver Unicode (FAIL). A temporary, session-guarded `type` handler delivers ASCII (when NORMAL blockers/commands are disabled for the session, config C) and Unicode, and handles composition. Hybrid D delivers all ASCII through bindings, but bindings shadow `type` for any key whose layout-resolved binding exists, so layout-dependent mismatch risk remains unproven on real layouts. Recommended direction for later design review: `type` for text, bindings only for modified characters and non-text keys. This blocks nothing yet, but real-layout evidence is pending.

## 2. Modified-character routing (callback phase)

Matrix: keys w x a 1 [ ; space x all 16 Ctrl/Shift/Alt/Meta subsets x with and without CDP text, 224 presses in A and 208 in C (Ctrl+W combinations skipped in C: they close the editor/window natively; see `skipped` in the results JSON).

- A (bindings): every combo reached the owner as the character value (shifted value when Shift is held), 224/224, both versions.
- C (`type` only): Ctrl combos (with or without text) reach neither `type` nor anything else, plain/Shift/Meta/Alt(with text) reach `type` with the exact char, except Alt+W and Alt+1 which VS Code binds natively (neither). Ctrl+X cut the line in two C presses (document leak, restored).
- Result: Ctrl/Alt/Ctrl+Alt characters are only reachable through keybindings. `mi<Alt-w>` and `ms<Ctrl-x>` are deliverable via scoped bindings (value = character, modifiers ignored by the owner).
- Action phase: 48/48 keys (`i a s` x all 16 modifier subsets) matched exactly one binding with the exact modifier string, both versions.
- Outside a pending session (fresh host, probe 8): Ctrl+A selects all, Alt+Down moves the line, Ctrl+X cuts the line (both versions). Ctrl+Shift+Alt+Down gave one selection (host/WM dependent, not conclusive). Note: the copy of this check at the end of probe 2 failed on 1.85.2 after the host restart (below) and is not authoritative.

## 3. Ordered buffering and replay (7 scenarios, both versions identical)

- Buffer: keys arriving during the 300-500 ms simulated lookup were buffered in sent order (`d`; `d, Escape`; 6 modified and non-character keys; 14 keys sent within 19 ms), each through the real binding with its identity string (`shift+w`, `alt+o`, `left`, `enter`, `ctrl+d`, `escape`).
- Reference failure: replay executed, in order, the commands of the real contributed NORMAL bindings read from the extension's `package.json` (`d` -> `miniHelix.deleteSelection`; the document showed the ordinary delete ` beta gamma`; `shift+w` -> `miniHelix.moveNextLongWordStart`; `alt+o` -> `miniHelix.expandSelection`; 14 rapid motions in order).
- Infrastructure failure: buffer discarded, no command, document unchanged. Successful lookup: buffered keys delivered in order to the replacement callback as characters (`d x X <escape>`).
- Limits (valid FAIL for generality): VS Code has no API to re-inject a keystroke or query the resolved keybinding. Keys with no extension binding (`ctrl+d`, native arrows) could not be replayed through `executeCommand`; `left` and `escape` used a fixture table (`cursorLeft`, `miniHelix.clearCount`); user or other-extension keybindings cannot be honored. Replay is faithful only for the extension's own bindings plus a closed native-command fixture. Selection results in this probe are not a Helix oracle.
- A 0 ms lookup response let following keys fall through to ordinary NORMAL dispatch (document deleted by real `d`), as expected after completion.

## 4. Selection projection matrix (225 readbacks per version, identical across versions)

Authoritative data: `results-<v>.json` -> `probe4.matrix` rows `[fixture, case, input, readback, selectionChangeEvents, authoritative]`. Positions `line:col`. Fixtures: LF/CRLF with and without final newline, empty (LF/CRLF), CRLF blank lines, non-BMP `a😀b`, combining `e+U+0301`.

- Kept as given (no merge/reorder): touching ranges `[a,b][b,c]`; reversed (anchor after head), including from EOF; mixed-direction pairs; primary-not-first and primary-last orders (`selections[0]` is preserved as primary; the secondary order is kept, not sorted); empty cursors; EOF cursor/range with and without final newline; CRLF-adjacent positions at `0:2` and `1:0`.
- Merged by VS Code: overlapping ranges -> union; nested -> the outer range; empty cursor inside/at the edge of a range -> the range; identical ranges and duplicate cursors -> one. The primary and direction of the surviving selection follow the first/outer one (see raw rows).
- Clamped: positions past the line end -> line end; past EOF -> last position.
- CRLF: `positionAt` of the offset between `\r` and `\n` returns the end of the line (`0:2`, offset 2); `offsetAt(0:3)` = 2; `validatePosition(0:3)` = `0:2`. No API path or real arrow/shift-arrow input produced a position between `\r` and `\n` (Right from `0:2` goes to `1:0`, offset 4; Shift+Right/Left likewise). So the CRLF gap is not representable and was never produced.
- Surrogate pairs: a selection endpoint inside a pair (`0:2` of `a😀b`) reads back snapped left to `0:1`; `document.positionAt(2)` itself still returns `0:2` (unvalidated). Real Right/Left steps over the pair (offset 1 -> 3).
- Real input: two cursors + Shift+Right merge when ranges touch/overlap (`0->1,1->2` then `0->3`, `0->4`).
- Host-view caveat (important): the extension host only learns the validated selection from a change event. Setting a selection that the main thread clamps back onto its current state emits no event, so `editor.selections` keeps the unvalidated local value for good (CRLF doc: set `0:3` while the cursor is at `0:2` -> readback `0:3`, 300 ms later still `0:3`; non-BMP `0:5`; empty document `5:99`). Rows with `authoritative=false` are of this kind: all empty-document rows (a single position, no differing sentinel) and the deliberate clamp rows. All other rows were obtained after a sentinel selection forced a change event.
- Determination for step 4: no reachable normalized shape that these fixtures produced loses information in VS Code projection, except representability limits that upstream invariants do not generate (gap inside CRLF, endpoint inside a surrogate pair). Deciding whether a reachable Helix selection (e.g. two ranges that VS Code would merge, or cursor semantics at EOF/CRLF) needs metadata requires the native oracle output and is PENDING: this probe provides only the VS Code side. Merge behavior (overlap, nested, touching-with-empty, duplicate) is the set of Helix selection shapes VS Code cannot represent; whether Helix can produce them after normalization is for the later comparison.

## 5. Stale edit race: does `TextEditor.edit` protect the base version?

Each variant: 250 trials per version, base `hello world`, cursor 5, native change = real INSERT typing of `k` (CDP) or `workspace.applyEdit` insert `W`; proposal = replace `[6,11)` with `WORLD` computed for the base version; validation `document.version === V` immediately followed by `editor.edit` with no await. Outcomes are classified from final text.

| Variant (both versions) | 1.143.1 | 1.85.2 |
|---|---|---|
| V1 key acked, then check+edit | 250 caught by sync check (host already saw the event) | same |
| V2 key not awaited, edit same tick | 250 edit first (valid serial) | 249 serial, 1 rejected |
| V3 key + helper delay 0-300 ms | 241 caught, 9 serial | 192 caught, 51 rejected(false), 7 serial |
| V4 applyEdit unawaited + edit | 250 edit first; native `applyEdit` returned false (it is version-guarded too) | 250 `edit` applied first, then native `applyEdit` also applied (`applyEdit` returned true 250/250; outcome `applied-before-native (valid serial)`) |
| V5 applyEdit + delayed helper | 250 caught | 250 caught |
| V6 key sent from a worker thread, host thread blocked 3-40 ms, then check+edit (stale mirror) | **250/250 `edit` returned false** | **245 false**, 5 legitimately ordered |
| V7 applyEdit started, host blocked 3-40 ms, then check+edit (stale mirror) | **250/250 false** | **249 false**, 1 ordered |

- Across 7 variants x 250 trials x 2 versions: `edit` threw 0; text corruption/duplication 0; edit applied on a changed base (`hellokWORLDd` shape) 0; selection anomalies 0 (cursor `0:6` after every rejection).
- Undo (20 trials per version): after a rejected edit, one `undo` restored the pre-typing text; document version advanced only by the native change (delta 1); cursor stayed `0:6`. So a rejected edit leaves no history entry or selection effect.
- Determination: the supported API protects the base version for changes the host has not yet seen. `TextEditor.edit` captures the host mirror version when called and the main thread rejects a different model version (returns `false`); the synchronous host-side check is required for changes the host has already seen (V1, V3, V5 caught them before the call). Reproducing the stale mirror needed a worker-thread key or a host busy-wait; a plain CDP key from the host thread arrives too late to race (V2).
- Limit: on 1.143.1 `workspace.applyEdit` was also version-guarded in V4 (returned false 250/250 after the edit applied first; not required by the contract). On 1.85.2 V4 showed no `applyEdit` rejection (returned true 250/250). Multi-document and notebook edits were not tested.

## 6. Version differences and incidents

- Differences: non-BMP via CDP key event (1.85.2 garbled); V3/V4 race interleavings differ in timing only; input surface differs (1.143.1 `native-edit-context`, 1.85.2 textarea) yet all route/composition verdicts are equal.
- Incident (1.85.2): the renderer/window restarted once per launch, always at about the same place in probe 2 config C (the press after `shift+alt+a`, i.e. `ctrl+shift+a` without text; 5 of 5 fresh launches), with `Extension host terminating: renderer closed the MessagePort`. It did not reproduce in an isolated `ctrl+shift+a` diagnostic and did not repeat after the restart, with or without `--disable-gpu`. Cause not isolated (Chromium logs `LatencyInfo vector size ... is too big` before it). The harness is restart-safe: the restarted host re-runs all probes from the start and overwrites results, so reported 1.85.2 data comes from the restarted host's complete run (raw `/tmp/hm-t1c-logs/<version>/run.log` shows probe 1 twice). Native shortcuts at the end of the 1.85.2 probe 2 failed only in that restarted host (probe 8 on a fresh host passes).
- No 1.143.1 restart occurred.
