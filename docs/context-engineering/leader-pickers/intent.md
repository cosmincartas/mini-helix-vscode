# Intent: leader key pickers

Sources are labeled: **[user]** stated by the user, **[repo]** seen in the
repository, **[proposed]** our inference, not yet confirmed.

## Problem

In Helix, you press Space (the leader key) and then a letter to open a picker.
Mini Helix has no leader key today. To find a file, an open editor, or a
symbol, the user must leave the Helix-style flow and use VS Code shortcuts.

The user wants three leader commands in NORMAL mode [user]:

| Keys | Opens |
| --- | --- |
| Space, then `f` | file picker for the whole workspace |
| Space, then `b` | picker of open editors in the current editor group |
| Space, then `s` | symbol picker for the current file |

The pickers are VS Code's own Quick Open lists, not a new custom picker [user].

## Definition of done

- In NORMAL mode, Space then `f` opens VS Code's file picker. It searches all
  files in the workspace [user].
- Space then `b` opens a picker of the open editors in the focused editor
  group only [user].
- Space then `s` opens VS Code's symbol picker for the current file [user].
- The three commands work in NORMAL mode in both writable and read-only text
  editors, when a text editor has focus [user]. This matches `gd` and `gr`
  [repo: `idleMotionWhen` in `scripts/keybindings.cjs`].
- They do nothing special in INSERT mode, when Mini Helix is suspended, or when
  focus is outside a text editor. Native input stays there [proposed, matches
  the rest of the extension].
- The README documents the new keys, like the other bindings [proposed,
  matches `README.md`].
- `npm test` passes, with tests for the new keys [proposed].

## Affected users and systems

- **Users of Mini Helix in NORMAL mode.** Space starts a key sequence instead
  of being silently blocked [repo: `space` is in the blocked keys list].
- **Keybindings.** They are generated by `scripts/keybindings.cjs` and stored in
  `package.json` [repo]. A new `space` chord joins the existing `g` and `m`
  chords.
- **Other chords and modes.** Space must not break `gw` label input or a
  pending `mr` replacement. Today Space cancels both [repo: `blocked` keys in
  `jumpWhen` and `surroundPendingWhen` bindings].
- **Language extensions.** The symbol picker shows symbols only if a language
  extension provides them [proposed, same limit as `gd`/`gr` in the README].

## Constraints

- Leader key is Space, fixed. No setting to change it. Users can rebind through
  VS Code's own keybindings [user].
- Scope is only `f`, `b`, `s` now. No user-defined leader mappings, no leader
  menu. More leader keys come later, one at a time [user].
- Use VS Code's native pickers. Do not build a custom picker [user].
- `b` lists only the current editor group. This differs from Helix, which lists
  all buffers; the user chose it on purpose [user].
- VS Code 1.85+ [repo: `engines.vscode` in `package.json`].
- The extension does not override VS Code's global `type` command and keeps
  native input outside NORMAL [repo: README, "What this version does"].

## Open questions

These are for design. Each has a proposed answer that follows how the
extension handles `g` chords today.

1. **Count before Space.** Example: `3` Space `f`.
   Proposed: the picker opens once and the count is cleared, as `gd` and `gr`
   ignore a count today.
2. **Unbound leader keys.** Example: Space then `x`, or Space then Escape.
   Proposed: nothing happens, no text is typed, and a pending count is
   cleared, like unbound `g` chords (`chordNoops`).
3. **Shift+s (workspace symbols, Helix `Space S`).** Not in scope now. It could
   be a later leader key.
4. **Helix's other `space` keys** (`F`, `j`, `/`, `y`, `p`, ...). Not in scope.
   Space then any of them should act as an unbound leader key (question 2).
